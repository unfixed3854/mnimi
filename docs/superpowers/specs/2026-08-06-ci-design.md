# CI pipeline

A GitHub Actions workflow that typechecks, tests, and builds the project on
every pull request and every push to `main` — closing issue #4.

## Problem

There is no `.github/workflows` at all. Nothing catches a broken build, a
type error, or a failing test before it lands on `main`. The project has two
independent toolchains (a Vite/React frontend typechecked by `tsc`, a Deno
server typechecked by `deno check`) plus a Tauri desktop shell that neither
gets exercised.

## Approach

One workflow file, two jobs, running in parallel:

- **`verify`** — typecheck + test + frontend build. Fast, and should fail
  fast independently of the desktop build.
- **`desktop-build`** — compiles the Tauri shell for Linux.

Neither job installs Java or the Android SDK. Both are pinned in
`mise.toml` for the mobile target, but nothing in this CI builds for
Android, so pulling `mise install node deno` (not a bare `mise install`)
keeps both jobs from paying for a toolchain they don't use.

Alternatives considered:

- **Dedicated setup actions** (`actions/setup-node`, `denoland/setup-deno`,
  `dtolnay/rust-toolchain` pinned by hand) instead of `mise`. Slightly more
  idiomatic per-tool caching, but the versions can silently drift from
  `mise.toml` since nothing forces them to match. Rejected in favor of exact
  parity with local dev.
- **Single sequential job** (typecheck → test → build → tauri build).
  Simpler YAML, but a slow Rust compile blocks on steps that have nothing to
  do with Rust, and a fast typecheck failure doesn't surface any earlier than
  the slowest step. Rejected — parallel jobs give real fail-fast behavior.
- **Full desktop matrix (Linux + macOS + Windows)**. 3x the runners and Rust
  compile time for a desktop build that isn't actually shipped to users yet.
  Rejected for now; revisit if the desktop build becomes a real release
  artifact.

## Triggers

```yaml
on:
  pull_request:
  push:
    branches: [main]

concurrency:
  group: ci-${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true
```

The concurrency group cancels a stale run when a PR gets pushed again —
otherwise every push queues its own full run and old ones burn minutes for
no reason.

## Job: `verify`

Runs on `ubuntu-latest`.

1. `actions/checkout@v4`
2. `jdx/mise-action@v2` with `install_args: node deno` — installs the exact
   Node and Deno versions pinned in `mise.toml`, skipping `java` and
   `android-sdk`.
3. `deno install` at the repo root (frontend deps) — matches the README's own
   setup instructions.
4. `deno install` inside `server/` — it has its own `deno.json` and
   `deno.lock`, independent of the root's.
5. `deno task build` — runs `tsc && vite build`. This is the frontend
   typecheck *and* the production-bundle check in one step; no separate
   typecheck command is needed since `tsc` already runs first.
6. `deno check main.ts` from `server/` — the server typecheck. Verified
   locally: this type-checks the whole server graph cleanly through
   `main.ts`'s imports. Test files are deliberately excluded from this step —
   `deno check some.test.ts` fails with `Import "vitest" not a dependency and
   not in import map`, because `vitest` isn't in `server/deno.json`'s import
   map (it's resolved from the root's `node_modules` when vitest itself runs
   the tests, not by `deno check`). This mirrors how the frontend build also
   doesn't typecheck via vitest — vitest runs tests, `tsc`/`deno check`
   typecheck source.
7. `deno task test` from the repo root — one `vitest run` covers both
   `src/**/*.test.ts(x)` and `server/**/*.test.ts` per `vitest.config.ts`.
   No secrets or network access needed: the AI-generation and image-write
   tests already mock their external calls (`vi.fn()`/`vi.mock`), and
   `server/db/testing.ts` gives every test run an isolated temp-file SQLite
   database.

## Job: `desktop-build`

Runs on `ubuntu-latest`, in parallel with `verify` (no `needs:` dependency).

1. `actions/checkout@v4`
2. `jdx/mise-action@v2` with `install_args: node deno`
3. `deno install` at the repo root
4. `dtolnay/rust-toolchain@stable` — installs Rust
5. `Swatinem/rust-cache@v2` — caches the Cargo registry and `target/` keyed
   on `Cargo.lock`
6. `apt-get install` the Tauri v2 Linux build deps: `libwebkit2gtk-4.1-dev`,
   `libayatana-appindicator3-dev`, `librsvg2-dev`, `libssl-dev`,
   `build-essential`, `curl`, `wget`, `file`, `libxdo-dev`
7. `deno task tauri build` — `tauri.conf.json`'s `beforeBuildCommand` is
   already `deno task build`, so this single command produces the frontend
   bundle, compiles the Rust binary, and produces the Linux bundles
   (`.deb`/`.AppImage`/etc.) in one step. No separate frontend-build step is
   needed in this job.

A `deno`-cache step (`actions/cache@v4` over `~/.cache/deno`, keyed on both
lockfiles) is added to both jobs so the desktop build in particular doesn't
re-fetch every dependency from scratch on every run.

## Error handling

No custom error handling — a failing step fails the job, a failing job
blocks the PR via GitHub's standard required-checks UI (which isn't
configured as part of this change; branch-protection rules are a separate,
repo-settings-level decision). No retries: flaky steps should be fixed, not
papered over.

## Testing

There's no way to unit-test a workflow file. Validation is: push this branch,
open a PR against `main`, and watch both jobs run in the Actions tab —
`verify` should pass in roughly the time `deno task build && deno task test`
takes locally, and `desktop-build` should produce Linux bundles without
manual intervention. If either job fails for a reason unrelated to real
project state (e.g. a missing apt package), fix the workflow file and push
again; the PR this ships in is itself the first real test of the pipeline.
