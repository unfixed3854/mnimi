# German Account Seed Devtools Design

## Goal

Add a development-only TanStack Devtools action that seeds the signed-in
account with a small German study deck. The seed is defined in the repository
so it is stable, reviewable, and free to use rather than being generated by
paid providers at runtime.

The seed contains one `German` deck with three language notes:

- `die Banane`
- `der Apfel`
- `das Haus`

Each note has several short cloze-deletion cards covering lexical meaning,
gender, and plural/context. The cards follow the same language-generation
rules as production cards: one `c1` deletion, German sentence context, an
English inline hint where needed, and `imageCue: true` only when the hidden
vocabulary is represented by the note image. Notes use the existing language
representation: `domain: "language"`, `language: "de"`, and noun metadata.

The repository also contains three deterministic PNG note images and the
deterministic German pronunciation audio files required by the seed cards.
The media is copied into the account's private storage when the seed is
created, so the normal image and audio HTTP routes serve it exactly as they
serve production-generated media.

Images are generated once as project assets and then committed. Pronunciation
MP3s are generated locally with the installed German `espeak-ng` voice and
encoded with `ffmpeg`, so refreshing the seed never requires a paid service.
The fixture records the exact asset names and the text used to produce each
audio file.

## User interaction

The existing TanStack Devtools shell gets a second plugin for seeding data.
The panel exposes a `Seed German` action and a small live status message.

When the signed-in account has no exact-name `German` deck, clicking the action
creates the seed immediately. When an exact-name `German` deck exists, the
first request only reports that replacement is required. The panel then asks
the user whether to remove and recreate that deck. Cancelling leaves all data
unchanged; confirming performs the replacement.

The panel disables the action while the request is pending, reports errors,
and reports whether the seed was created or replaced. It uses the same browser
confirmation pattern as the existing SRS Devtools panel.

## Server architecture

Add a development-only `debug.seedGerman` procedure protected by the existing
authenticated-and-devtools-enabled middleware.

Its input is an explicit `replace` boolean:

- `replace: false` checks for an owned exact-name `German` deck. If one exists,
  it returns a replacement-required result without changing the database;
  otherwise it creates the seed.
- `replace: true` rechecks ownership and exact name inside the write transaction,
  deletes the existing owned `German` deck and its cascaded notes/cards, then
  inserts the checked-in seed.

The seed fixture lives in a focused server module and contains declarative
deck, note, card, image, and audio references. The binary fixtures live beside
it under a clearly named seed-assets directory. The router supplies account
ownership, generated IDs, timestamps, and initial FSRS due dates, then copies
the referenced media to account-scoped storage and records the generated
paths. Creation and replacement happen under `withWriteLock` and one database
transaction for database state; media files are copied with cleanup on failure
so a failed operation does not leave an unusable partial seed.

The card fixture is validated with the same cloze and image-cue predicates used
by generated-note validation and note saving. Every language card is eligible
for pronunciation through `ttsTextForCard`, and its audio row is inserted as
ready with a checked-in MP3 rather than as pending work. No ElevenLabs,
OpenRouter, or other paid provider is called by the seed action.

The delete is scoped by both the authenticated user ID and the exact deck name.
It cannot remove another account’s deck or any differently named deck. The
existing database cascade removes the deck’s notes and cards. The seed
creates deterministic image and audio files. Before a confirmed
replacement removes database rows, the server records their image and audio
paths and removes those owned files after the transaction succeeds. This
prevents old account media from accumulating while keeping failed
transactions recoverable.

The procedure returns a small result suitable for the panel, including whether
the operation needs confirmation, the resulting deck ID, and created/replaced
note and card counts. Devtools-disabled and unauthenticated requests retain
the existing error behavior.

## Client integration

Add a typed `useSeedGerman` mutation in the debug API module. On successful
creation or replacement it invalidates the debug summary, decks, notes, cards,
and review-related query keys so the signed-in application immediately sees
the new content, images, and playable audio.

Add a `GermanSeedDevtoolsPanel` and register it in `MnimiDevtools` with its own
plugin ID and name. The panel owns only interaction state; all seed content and
ownership decisions remain server-side.

## Error handling and safety

- No request accepts a user ID from the client.
- The server checks the existing deck again after confirmation, preventing a
  stale confirmation from deleting a newly changed or differently owned row.
- A cancelled confirmation makes no second request and no database change.
- A failed transaction or media copy is surfaced in the panel and leaves
  existing content intact; cleanup removes only files created for that failed
  attempt.
- The action is available only when the client is in development mode and the
  server was started with `--devtools`, matching the existing SRS tools.
- The seed action never invokes paid image or TTS providers. Regenerating the
  fixture assets is an explicit repository-maintenance task, not a user action.

## Verification

Server tests cover:

- creating the three-note seed for an account with no `German` deck;
- validating cloze structure, image-cue context, ready audio state, and image
  paths for every seeded note/card;
- returning replacement-required without changing an existing deck;
- replacing only the signed-in account’s `German` deck and cascaded content;
- removing replaced seed media without touching another account’s files;
- preserving other owned decks and another account’s similarly named deck; and
- rejecting the procedure when server devtools are disabled.

Client tests cover:

- rendering the new plugin through TanStack Devtools;
- successful creation feedback;
- confirmation before replacement;
- cancellation without a replacement call; and
- successful replacement feedback and query invalidation wiring; and
- media rendered through the normal authenticated image/audio routes.

The full project test suite, API type-check, and production build will be run
with the repository’s `deno` tasks.
